Обе платформы, один serverless-адаптер

14 октября 2026 · подготовлен код для отдельного игрового проекта Supabase. Публикация, создание аккаунтов и реальные платежи не выполнялись. Проект трекера механик остаётся отдельным.

Что реализовано

  • Облачные профили с версиями, последовательной очередью записей и резервной местной копией при конфликте двух устройств.
  • Яндекс: подписанное подтверждение личности, заказ с непредсказуемым UUID, проверка HMAC SHA-256 на сервере, привязка заказа к аккаунту/SKU/платформе, неизменяемый состав награды.
  • Рубины, весь набор бустеров, пропуск конкретного сезона, журнал покупки и версия профиля записываются одной транзакцией PostgreSQL. Повтор токена не начисляет награду второй раз. В базе хранится хеш токена.
  • Клиент вызывает consumePurchase после успешной местной записи и подтверждённой облачной версии. Ошибка оставляет покупку для повторной проверки; раздел «Сохранение» позволяет принять облачную копию и экспортировать резервную.
  • Веб: анонимный вход в игровое облако, привязка почты и вход по ссылке для другого устройства. Платёжный адаптер имеет точку подключения, но checkout выключен до выбора провайдера. Публичная веб-версия больше не выдаёт тестовые покупки.

Облако поддерживает обе платформы. Автоматического объединения Яндекс-аккаунта и веб-аккаунта сейчас нет. Веб-восстановление требует подтверждённой почты; до привязки доступ зависит от сохранённой сессии браузера.

Подключение стенда

  1. Создать отдельный игровой проект Supabase. Включить Anonymous Sign-ins. Настроить почтовый канал и разрешённые Auth redirect URLs для игровых адресов. Добавить домены игры в CORS функции.
  2. Проверить миграцию supabase/migrations/202610140001_game_profiles.sql и применить её к игровому проекту. Она создаёт только таблицы game_* и функции доступа с правами service_role; прямой доступ ролей anon/authenticated закрыт.
  3. В серверных секретах Edge Functions задать значения из таблицы ниже. Клиент получает только URL проекта и публичный publishable key.
  4. На стенде Яндекса проверить структуру настоящего подписанного player envelope и указать путь до ID в YANDEX_PLAYER_ID_PATH. Схема ID не угадывается; без этого значения вход закрыт. Проверить формат signed purchase: status waiting, product.id, token, developerPayload. Зарегистрировать SKU из game_products, включая seasonPass, и цены в каталоге платформы.
  5. Развернуть функцию game-api. В config.toml отключена внешняя JWT-проверка, чтобы подписанный вход Яндекса работал до создания сессии. Каждый защищённый action внутри функции проверяет bearer через auth.getUser.
  6. Заполнить assets/platform-config.js публичными данными игрового проекта, оставить webPaymentsEnabled: false. Собрать игру и выполнить проверку стенда перед включением покупок.

Команды после выбора игрового проекта; в этой работе они не выполнялись:

supabase link --project-ref GAME_PROJECT_REF
supabase db push
supabase functions deploy game-api

Секреты задаются в панели Edge Functions. Не помещать их в браузерный конфиг, Git или экспорт игрового профиля.

Контракт веб-провайдера

webProvider и getIntent в game-api пока отключены и возвращают 503. После выбора провайдера нужно реализовать checkout для принадлежащего пользователю веб-заказа: сервер получает цену из своего каталога, передаёт intentId в metadata и возвращает HTTPS checkoutUrl.

Отдельная функция webhook должна проверить подпись провайдера, статус, сумму, валюту, productId и владельца заказа. Только после проверки она вызывает game_purchase_claim с хешем ID транзакции и актуальной версией. При конфликте профиль перечитывается и операция повторяется. Redirect браузера не является подтверждением оплаты. До этого адаптера веб-покупки остаются выключены.

Проверено локально

node tools/test-serverless.mjs
node tools/test-cloud-client.js
npx tsc --noEmit
npx --yes deno@2.5.4 check --no-config --no-lock --node-modules-dir=none supabase/functions/game-api/index.ts

Тест миграции запускает PostgreSQL/PLpgSQL через PGlite без сети, Docker и файлов игроков: все SKU/наборы, повтор, чужой аккаунт, устаревшая версия, неизменяемый заказ, сезон, откат поздней ошибки, права доступа, авторизация, CORS и подписи. Клиентские проверки используют управляемую имитацию SDK: отказ localStorage, обрыв облачной записи, повтор consume и восстановление.

Сериализованный PostgreSQL в PGlite проверяет конфликт версий, но не конкуренцию отдельных соединений. На стенде остаются реальные SDK, Auth/почта, CORS платформы, два устройства, одновременные транзакции, перезапуск между оплатой и выдачей, длительный офлайн и смена сезона.

Границы текущего этапа

  • Игровые награды, траты и результаты уровней ещё поступают от клиента. CAS защищает от случайного перезаписывания оплаченной версии, но не заменяет серверную экономику и античит. Следующий этап — серверные команды с operationId и проверкой правил для подарков, энергии, наград и трат.
  • Первый профиль импортируется с устройства. Маркеры чеков и premium-флаги при обычном save назначаются сервером; остальные исходные игровые данные пока доверенные. Нужен согласованный регламент миграции старых игроков.
  • Старые покупки без созданного сервером developerPayload не принимаются автоматически и не consume-ятся. Их необходимо отдельно сверить/мигрировать перед запуском магазина. Ошибочный старый чек в списке блокирует пакет проверки, оставляя чеки на платформе.
  • Нет веб-провайдера, обработки возвратов/отмен и автоматического объединения аккаунтов. Операторские инструменты лайв-опса и централизованный сбор полной телеметрии остаются отдельными пунктами отчёта.

Тестовая выдача доступна только на localhost/127.0.0.1 при явном ?testpayments=1. Использовать отдельный тестовый профиль; в публичной версии этот параметр не включает покупки.

Подписанные покупки Яндекс Игр, подписанный player, проверка Auth в Edge Functions, анонимный вход, серверный generateLink, обмен verifyOtp, PGlite.
